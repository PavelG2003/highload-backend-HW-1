Мониторинг REST API

Учебный проект. Два экземпляра приложения, Prometheus, Grafana, генератор дашборда и фоновая нагрузка. Данные хранятся в памяти каждого экземпляра.

## Запуск всего стенда

Нужны Docker с Linux-контейнерами и Docker Compose v2. Для Windows подходит Docker Desktop с WSL 2. Локальные Java, Maven и Python для запуска через Compose не требуются. При первой сборке нужен интернет для скачивания образов и Maven-зависимостей.

Команды выполняются из корня проекта. В Windows PowerShell:

```powershell
Copy-Item .env.example .env
docker compose up
```

В Linux/macOS:

```bash
cp .env.example .env
docker compose up
```

Compose собирает образ приложения при первом запуске. После изменения Java-кода используйте `docker compose up --build`. Для запуска в фоне добавьте `-d`.

После готовности сервисов генератор автоматически публикует дашборд, затем запускается нагрузка. Ожидается, что графики появятся в течение 2–3 минут после готовности стека; первоначальное скачивание и сборка могут занять дополнительное время. Приложение, запущенное из IntelliJ на порту 8080, нужно остановить либо изменить `APP_1_PORT` в `.env`.

## Метрики и лейблы

Метрики доступны по GET /metrics в формате Prometheus.

| Метрика | Назначение |
|---|---|
| handler_requests_total | Счётчик завершённых бизнес-запросов, включая ошибки; используется для расчёта RPS и ошибок по HTTP-кодам |
| handler_request_duration_seconds_bucket | Бакеты гистограммы длительности запросов; используются для расчёта p50, p95 и p99 |
| handler_request_duration_seconds_count | Количество измеренных запросов |
| handler_request_duration_seconds_sum | Суммарная длительность запросов в секундах |

Используются следующие лейблы:

| Лейбл | Значение |
|---|---|
| pod | Идентификатор экземпляра из переменной POD_ID |
| datacenter | Датацентр из переменной DATACENTER |
| method | HTTP-метод: POST, GET или PUT |
| route | Шаблон пути: /items или /items/{id} |
| status | HTTP-код ответа, например 200, 201, 400 или 404 |
| le | Верхняя граница бакета в секундах; присутствует у метрики бакетов |

В route используется шаблон /items/{id}, а не фактический
идентификатор записи. Это предотвращает создание отдельного
временного ряда для каждого ID.

RPS рассчитывается через rate(handler_requests_total[...]).
Ошибки выделяются по status=~"[45].." и группируются по status.
Служебные /health, /metrics и /handlers в бизнес-метрики не входят.

## Почему для latency выбрана гистограмма

Для длительности запросов используется классическая гистограмма.
Она позволяет рассчитывать p50, p95 и p99, в том числе для
нескольких экземпляров приложения.

Все экземпляры используют одинаковые границы бакетов. При выборе
нескольких подов сначала вычисляется rate для бакетов каждого
экземпляра, затем значения суммируются с сохранением le,
после чего применяется histogram_quantile.

Пример общего p95:

histogram_quantile(
  0.95,
  sum by (le) (
    rate(handler_request_duration_seconds_bucket[1m])
  )
)

Готовые перцентили Summary нельзя корректно объединить простым
усреднением: среднее p95 двух подов не является общим p95.
Гистограмма позволяет объединять распределения до вычисления
перцентиля.

Полученные перцентили приближённые: точность зависит от выбранных
границ бакетов.
